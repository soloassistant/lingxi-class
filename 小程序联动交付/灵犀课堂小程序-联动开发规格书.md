# 灵犀课堂 · 微信小程序（联动版）开发规格书

> 交付对象：外部开发方
> 目标：做一个小程序，与已上线的网页版**共用同一套账号与同一份数据**
> 本文档中的接口地址、字段名、错误码、数据结构**均为实测所得**，不是推测。凡标注「实测」的条目可直接照抄。

---

## 0. 一句话说清要做什么

网页版（灵犀课堂）已经上线，跑在 WorkBuddy 云服务上。现在要做一个微信小程序，**不是复制一份数据**，而是让小程序成为同一套后端的第二个客户端：

- 用户在小程序用**手机号 + 短信验证码**登录 → 登进去的就是**他在网页版的那个账号**
- 他在手机上看得到的课程、学情、错题，就是他网页版里的那些
- 手机上学完，回到电脑前接着学，进度是连续的

**核心约束：小程序不建自己的数据库、不建自己的账号体系。** 所有数据读写都打到网页版那套云服务上。

---

## 1. 架构

```
                  ┌─────────────────────────────────────────────┐
                  │        WorkBuddy 云服务（唯一数据源）          │
                  │                                             │
   网页版 ────────►│  Auth      手机号/邮箱 + 短信或邮件验证码        │
  (已上线)         │  Database  PostgREST，7 张表，RLS 按用户隔离   │
                  │  LLM       模型网关（流式）                   │
   小程序 ────────►│                                             │
   (本次要做)      └─────────────────────────────────────────────┘
```

两个客户端访问的是**同一个云环境**。这一点已经实测确认：

用同一个 `publishableKey` 分别请求网页版域名和小程序网关，取回的数据**逐条相同**：

| 请求目标 | 返回 |
|---|---|
| `https://bb6ae4d03fbd4b109cbbe6dbbc84502d.app.workbuddy.host/.cloud/database/rest/analytics_events` | 14 行，id 从 11 起 |
| `https://mp-api.app.workbuddy.host/.cloud/database/rest/analytics_events` | 14 行，id 从 11 起（**完全相同**） |

所以「联动」不需要任何同步中间件、不需要定时任务、不需要双向复制 —— 本来就是同一份数据。

### 1.1 为什么小程序走 `mp-api.app.workbuddy.host`

微信小程序的网络请求只能打**已登记的域名白名单**，且微信不接受通配符、白名单条数有上限。
所以小程序用的不是各应用自己的域名，而是平台统一的固定网关：

| 环境 | 网关 |
|---|---|
| 生产 | `https://mp-api.app.workbuddy.host` |
| 预发 | `https://mp-api.app-staging.workbuddy.host` |

（实测：预发网关当前不可达，**请使用生产网关**。）

这个网关靠请求头里的 `publishableKey` 决定把请求转发到哪个云环境。因此：

> **小程序必须使用「灵犀课堂」网页版应用的那一个 `publishableKey`。**
> 用错 key 就会连到另一个云环境，数据不通。

## 2. 接入参数

```js
// 这两个值直接照抄，不要改
const CLOUD_ENDPOINT  = 'https://mp-api.app.workbuddy.host'
const PUBLISHABLE_KEY = 'wbpk_Pq3DhJIr74vvC8YpuqkMPA_lgoEQ7iPSjSnnQx9ZsLOpjoB6dFoKCSh'
```

关于 `publishableKey` 是否算泄露：**不算**。它本来就是公开值，已经写在网页版前端源码里，任何人都能看到。
它只用来标识「你属于哪个应用」，**不承担鉴权作用**。真正的权限由用户登录后拿到的 `access_token` + 数据库 RLS 决定。

### 2.1 请求头（如果手写请求时需要）

| 头 | 值 |
|---|---|
| `x-wb-webapp-access-key` | 上面的 `PUBLISHABLE_KEY` |
| `Authorization` | `Bearer <access_token>`（登录后才有） |
| `Content-Type` | `application/json` |

**注意正确的头名是 `x-wb-webapp-access-key`。** 实测用其他名字（如 `x-publishable-key`）会被网关当成未带凭据，返回 `401 invalid_client`。

### 2.2 有一个必须知道的运行风险

网页版应用的云服务会校验请求来源（`Origin`）。实测：

| 请求特征 | 结果 |
|---|---|
| 带错误 `Origin`（如 `https://evil.example.com`） | **403 拒绝** |
| 不带 `Origin` | **放行** |

微信小程序的 `wx.request` **不发送 `Origin` 头**，所以当前可以正常访问（实测通过）。

但这意味着：**这条通路依赖「小程序不发 Origin」这一既有行为**。如果平台后续收紧来源校验，小程序侧可能被拒。
这不是需要你们解决的问题，但要知道它的存在 —— 一旦小程序请求开始返回 403，先怀疑这里，而不是先去改代码。

## 3. SDK 接入（推荐方式）

平台提供了官方 SDK，**请使用它，不要手写 `wx.request` 包装云服务接口**。

### 3.1 安装

在**小程序源码根目录**（与 `app.json` 同级）建 `package.json`，然后：

```bash
npm install @tencent-ai/workbuddy-cloud-sdk@dev
```

然后在微信开发者工具里执行「工具 → 构建 npm」。

**不要指定版本号、不要用 `latest`** —— 该 SDK 在 `dev` 频道持续更新，锁版本会把应用冻结在旧行为上。

### 3.2 初始化

新建 `utils/cloud.js`：

```js
const { createMiniProgramWorkBuddyCloud } = require('@tencent-ai/workbuddy-cloud-sdk/miniprogram')

const cloud = createMiniProgramWorkBuddyCloud({
  endpoint: 'https://mp-api.app.workbuddy.host',
  publishableKey: 'wbpk_Pq3DhJIr74vvC8YpuqkMPA_lgoEQ7iPSjSnnQx9ZsLOpjoB6dFoKCSh',
})

module.exports = { cloud }
```

要点：

- **两个参数都必须传。** 小程序里没有 `location.origin`，SDK 没有同源回落可用，漏传 `endpoint` 会在初始化时就报错。
- 只用 `/miniprogram` 子路径导出的这个工厂函数。**不要**从根路径导入 `createWorkBuddyCloud` 再自己拼装 polyfill —— 顺序错了会「能构造成功、一发请求就失败」。
- 返回的客户端形状与网页版一致：`cloud.auth` / `cloud.database` / `cloud.storage` / `cloud.llm`。

SDK 版本参考（实测 npm 上的 `dev` 版本）：`0.1.3-dev.c090db7.202610050023`。

### 3.3 建议同时装诊断适配器

把平台的诊断 helper 复制到 `utils/workbuddy-cloud-diagnostics.js`，初始化时包一层：

```js
const { createDiagnosticWx } = require('./workbuddy-cloud-diagnostics')

const cloud = createMiniProgramWorkBuddyCloud({
  endpoint: CLOUD_ENDPOINT,
  publishableKey: PUBLISHABLE_KEY,
  wx: createDiagnosticWx(wx),      // ← 只多这一行
})
```

它会在请求失败时往 vConsole 打一行 `[WorkBuddy Cloud] request failed`，含方法、URL、HTTP 状态、错误码。
**小程序真机调试时这是唯一的排错手段** —— 因为服务端拒绝（如域名未加白名单）在客户端只表现为一个笼统的失败。

## 4. 登录：手机号 + 短信验证码

**与网页版是同一套登录方式**（网页版前端已有手机号页签，走的是同一个通道）。用户在小程序登录后，拿到的就是他在网页版的账号。

### 4.1 为什么不是微信一键登录

微信登录在这个应用上**用不了**，实测报错：

```
POST /.cloud/auth/v1/login-wechat
{"error":"access_denied","error_description":"小程序未授权给 WorkBuddy"}
```

原因是平台的两类应用形态是分开的：

| 应用类型 | 支持的登录方式 | 说明 |
|---|---|---|
| Web 应用（灵犀课堂就是这个） | 邮箱、**手机号** | 平台文档写明「web app supports email login only」 |
| 小程序应用 | 邮箱、手机号、微信 | 但那是**另一个云环境**，数据不与网页版相通 |

要让小程序和网页版同账号，就必须让小程序连**网页版的云环境**；而那个环境下没有微信登录 provider。
用微信登录会得到一个小程序侧的独立身份，与用户的网页版账号是两个人，数据读不到。

**所以：手机号登录不是退而求其次，它是唯一能实现「同账号」的方式。**

### 4.2 完整流程（实测可用）

手机号验证码通道**已确认开通**。证据：服务端返回了来自短信服务的真实错误（`PhoneNumberInBlacklist`、`1 条/分钟`限流），说明它真的在调用短信服务，而不是「能力未接入」。

```
① wx 端收集手机号
   ↓
② cloud.auth.signInWithOtp({ phone })
   → POST /.cloud/auth/v1/verification
   ← { verification_id, expires_in: 600 }
   ↓
③ 界面进入「输入验证码」态，保存上一步返回的 handle（含 verify 闭包）
   ↓
④ 用户填 6 位验证码
   ↓
⑤ handle.verify({ token })        ← 注意：不是 sendOtp，不是再发一次
   → POST /.cloud/auth/v1/verification/verify   （换一次性 verification_token）
   → POST /.cloud/auth/v1/signin  或  /.cloud/auth/v1/signup   （由 isExistingUser 自动决定）
   ← 会话 { access_token, refresh_token, expires_in, sub, ... }
   ↓
⑥ 登录完成，之后所有 database / llm 请求自动带上会话
```

**关键实现要求：**

1. **用 `signInWithOtp`，不要用 `sendOtp`。** `signInWithOtp` 返回的对象带 `verify()` 闭包，它会根据 `isExistingUser` 自动决定走登录还是注册。`sendOtp` 只返回一个裸的 `verificationId`，你们得自己判断新老用户 —— 而判断依据 `is_user` 在实测响应里**并没有返回**（见 §4.5），所以自己判断大概率会错。

2. **发送与验证必须是两个独立的用户动作。** 点「获取验证码」只发送，点「登录」只验证。
   **绝不能在「登录」按钮里再次调用发送** —— 包括用户输错验证码后重试的情况。

3. **验证码态要在事件之间保留。** 存在 `Page` 的 `data` 里或页面级变量里，不要放在按钮回调的局部作用域。

4. **换手机号要重新发码。** 如果用户改了输入的手机号，而手上还是没有对应验证码，应提示重新获取，**不要**拿着旧 handle 去验证。

5. **发送中与提交中都要禁用按钮**，防止重复点击。重发倒计时只约束「发送」，不能把「提交」也锁住。

### 4.3 手机号格式（实测踩过的坑）

服务端对手机号的校验规则是：

```
^$|^\+[1-9][0-9]{0,3}\s[0-9]{4,20}$
```

注意 **国家码与号码之间必须有一个空格**。实测 `+8613000000000` 会报参数格式错误：

```json
{"code":"INVALID_ARGUMENT","error_code":3,
 "error_description":"invalid SendVerificationCodeRequest.PhoneNumber: value does not match regex pattern ..."}
```

**但是：不要把手机号自己拼成 `+86 xxx` 再传。**
SDK 内部已做归一化 —— 中国大陆号码会被它转成 `+86 <号码>`，其他国家的原样保留。
**直接把用户输入的号码原样传给 SDK 即可**（`13800138000` 或 `+86 13800138000` 都行）。

如果你们在应用层也做一次 `+86` 拼接，就会变成双重归一化而出错。

### 4.4 错误处理

错误要按 `error.kind` 分支，**不要靠匹配错误文案**（文案会变）。

| 情况 | 处理 |
|---|---|
| `kind === 'network'` 或 `'backend-unavailable'` | 「网络异常，请稍后重试」，**保留当前状态**，不要清掉已拿到的 handle |
| `kind === 'unauthenticated'` 或 `'invalid_grant'` | 需要重新登录 |
| 文案含 `not support` / `not enabled` / `disabled` | 短信通道未开通 → 明确告知，不是「验证码错了」 |
| 文案含 `frequen` / `too many` / `rate` / `频繁` | 「发送过于频繁，请稍后再试」 |
| 文案含 `expired` / `invalid.*code` / `验证码` | 「验证码不正确或已过期」 |
| `resource_exhausted`（实测 HTTP 429） | 实测原文：`Your phone can receive up to 1 text message per minute.` 同一个号 1 分钟内只能收 1 条 |

**文案纪律：**

- **绝不暴露「这个手机号是否已注册」。** 发送成功的提示统一措辞，不要区分「欢迎回来」和「将为你创建账号」到能被用来探测账号存在性的程度。
- 验证码有效期 **10 分钟**（实测 `expires_in: 600`，SDK 侧文档写 5 分钟，以服务端返回的 `expires_in` 为准，界面提示建议写「10 分钟内有效」）。

### 4.5 一个已知的接口缺口，需要你们兜住

实测 `POST /.cloud/auth/v1/verification` 的成功响应**只有两个字段**：

```json
{ "verification_id": "eyJhbGciOiJSUzI1NiIs...", "expires_in": 600 }
```

**没有 `is_user` 字段。**

而 SDK 的 `signInWithOtp` 是按 `payload.is_user === true` 来判断新老用户的，取不到就是 `false`。
后果：如果这个手机号**已经注册过**，SDK 可能仍按「新用户」走注册分支。

**要求：**

- 一律使用 `signInWithOtp` 返回的 `verify()` 闭包完成登录，**不要在应用层自己判断新老用户**。
- 如果实测发现已注册手机号登录时报「已存在」类错误，请**记录下来并反馈**，不要在前端做「先试注册、失败再试登录」这种兜底 —— 那会在登录失败时产生误导性的错误提示。
- 界面文案上，发送成功后不要断言「已为你创建账号」。

### 4.6 会话生命周期

SDK 自己管理会话，你们不要自己存 token 到 `wx.setStorageSync`。但要知道它的行为：

```js
// 会话对象结构（实测自 SDK 源码的解析逻辑）
const session = {
  accessToken:  payload.access_token,                                  // 必需，缺失即抛错
  refreshToken: payload.refresh_token,
  expiresAt:    Date.now() + payload.expires_in * 1000,                // 毫秒时间戳
  user: { id: payload.sub, isAnonymous: payload.is_anonymous === true, raw: payload }
}
```

- SDK 只在本地存 **access token 和一个不透明的刷新句柄**（`wbrt_...`）。**微信侧的 provider token 不会落到客户端。**
- `getSession()` 会在临近过期时自动刷新；只有需要强制刷新时才用 `refreshSession()`。
- `getUser()` 会真的打 `GET /.cloud/auth/v1/user/me`，需要服务端确认身份时用它。
- **绝对不要**把 token 打到日志、塞进 URL 或上报到埋点。

### 4.7 登录态门禁（必须有）

读写任何用户数据之前都要先查会话：

```js
const { data: session, error } = await cloud.auth.getSession()
if (error || !session) {
  // 显示登录界面，不要继续
  return
}
```

**严禁**用以下方式「绕过」未登录状态：

- ❌ 匿名登录（`signInAnonymously`）
- ❌ 只在 `wx.setStorageSync` 里造一个假用户
- ❌ 用 mock 会话让受保护数据「看起来能用」
- ❌ 把本地缓存当成用户数据源

受保护的数据**必须**有真实身份。这是硬要求，不是建议。

## 5. 数据模型

### 5.1 表清单

| 表 | 用途 | 单行含义 |
|---|---|---|
| `courses` | 课程 | 一门课（含大纲、幻灯片、回放） |
| `student_profiles` | 学生画像 | 一人一行 |
| `student_facts` | 长期记忆条目 | 老师记住的每一条具体事实 |
| `student_sessions` | 课堂记录 | 每节课的小结与逐字稿 |
| `analytics_events` | 埋点 | 一次事件 |
| `device_ledger` | 设备台账 | 风控用，**客户端不可直接读写** |
| `phone_ledger` | 手机号台账 | 风控用，**客户端不可直接读写** |

### 5.2 字段（以下均为实测的表定义）

**`courses`**

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | bigint (PK) | 自增 | 数据库行 id |
| `owner_id` | text | `auth.uid()` | **不要传这个字段**，由服务端填 |
| `course_id` | text | — | 课程在客户端的 id，两端靠它对上 |
| `data` | jsonb | `'{}'` | 完整课程对象（结构见 §5.3） |
| `created_at` | timestamptz | `now()` | |
| `updated_at` | timestamptz | `now()` | 同步靠它比新旧 |

**`student_profiles`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint (PK) | |
| `owner_id` | text | 服务端填 |
| `grade` | text | 学段，如 `小学` |
| `system` | text | 课程体系，如 `cn` |
| `goal` | text | 学习目标 |
| `level` | text | 水平 |
| `teaching_style` | text | 偏好讲法 |
| `pace` | text | 节奏 |
| `notes` | text | 备注 |
| `sessions_count` | integer | 累计课次 |
| `total_seconds` | integer | 累计时长（秒） |
| `phone` | text | 登录手机号 |
| `created_at` / `updated_at` | timestamptz | |

**`student_facts`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint (PK) | |
| `owner_id` | text | 服务端填 |
| `kind` | text | 取值见下 |
| `content` | text | 事实正文 |
| `subject` / `topic` | text | 学科 / 知识点 |
| `confidence` | double | 列默认 `0.6`；**客户端读取时兜底 `0.7`** —— 两个值都要有，不是同一个值，见下方说明 |
| `hits` | integer | 命中次数，默认 `0` |
| `last_seen` | timestamptz | 最近一次出现 |
| `source` | text | 来源 |
| `created_at` | timestamptz | |

> ⚠️ **`confidence` 有两个不同的默认值，别只记一个。**
>
> | 场景 | 值 | 来源 |
> |---|---|---|
> | 新行插入、字段没给 | **`0.6`** | 数据库列默认值 |
> | 读取历史数据、字段缺失 | **`0.7`** | 网页版 `normalizeFacts()` 的客户端兜底 |
>
> 网页版原文：`confidence: typeof f.confidence === 'number' ? f.confidence : 0.7`。
> 小程序读取 `student_facts` 时要采用**同样的兜底**，否则同一条记忆在两端显示的置信度会不一样。
> 写入时不需要自己填（走列默认）。

> 另外 `normalizeFacts()` 还会**丢弃脏数据**：`content` 不存在、不是字符串、或去空白后为空的事实条目**直接扔掉**。
> 并且它用的是 `Object.assign({}, f, {...})` **保留原始字段再覆盖**（不是白名单式重建）——
> 早期版本写成白名单重建，把 `id`（删除按钮要用）和 `subject`（学科标签要用）丢掉了。
> **归一化的原则是「补齐/纠正」，不是「裁剪」。**

`kind` 的取值与中文标签（与网页版一致，不要另起一套）：

| `kind` | 标签 |
|---|---|
| `weak` | 薄弱点 |
| `strength` | 优势 |
| `preference` | 偏好 |
| `progress` | 进度 |
| `misconception` | 易错点 |
| `context` | 背景 |

**`student_sessions`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint (PK) | |
| `owner_id` | text | 服务端填 |

### 5.3 课程对象（`courses.data` 的内容）

这是两端共用的数据契约，**字段名必须与网页版完全一致**，否则同一门课在两端的渲染会互相破坏。

```jsonc
{
  "id": "c_xxxxxxxx",          // 课程在客户端的 id，对应表里的 course_id
  "title": "分数的初步认识",      // 课程名
  "subject": "数学",
  "grade": "小学",
  "level": "基础巩固",
  "duration": "45 分钟",
  "progress": 0.35,            // [0,1] 学习进度
  "saved": true,               // 是否已存入「我的课程」
  "updatedAt": 1759000000000,  // 本地最后修改时间（毫秒），同步时比大小
  "syncState": "synced",       // 'synced' | 其他表示待同步

  "slides": [ /* 幻灯片对象数组 */ ],
  "boards": [ "..." ],         // 白板内容，字符串数组
  "boardNames": [ /* ... */ ],

  "outline": {
    "stages": [ /* 阶段对象数组 */ ],
    "knowledgePoints": [ /* 知识点 */ ],
    "homework": [ /* 作业 */ ]
  },

  "replay": { "events": [ /* ... */ ] }   // 可为 null
}
```

**字段纪律（这是网页版 `normalizeCourse()` 的逐条行为，请照此实现，不要自己简化）：**

| 字段 | 处理规则 |
|---|---|
| （整个课程） | 不是对象 → **返回 `null`，整条丢弃** |
| `slides` | 必须是数组；**且只保留其中的对象元素**（`filter(asObject)`，字符串/null 丢掉） |
| `boards` | 必须是数组；**且只保留字符串元素** |
| `boardNames` | 必须是数组（不做元素过滤） |
| `outline` | 必须是对象，否则置 `null` |
| `outline.stages` | 必须是数组；**且只保留对象元素** |
| `outline.knowledgePoints` | 必须是数组（不做元素过滤） |
| `outline.homework` | 必须是数组（不做元素过滤） |
| `replay` | 若存在但 `replay.events` **不是数组 → 整个 `replay` 置 `null`**（半截回放比没有更糟） |
| `title` | 是非空字符串就用它，否则 `未命名课程` |
| `subject` / `grade` / `level` / `duration` | 不是字符串 → 归空字符串 `''` |
| `progress` | 不是数字 → `0`；是数字 → 夹到 `[0, 1]` |

> 注意 `slides` / `boards` / `outline.stages` 的**元素类型过滤**容易漏 —— 只写「必须是数组」不够，
> 网页版还会把数组里的脏元素剔掉。漏了这条，两端同一门课会渲染出不同的空行/空白项。
>
> 另：网页版 `title` 兜底处有一句死代码 `o.rawOutline ? '未命名课程' : '未命名课程'`（两个分支同值，是遗留写法）。
> 小程序**不必复制这个写法**，直接兜底 `未命名课程` 即可 —— 行为一致。

**写入时不要传 `owner_id`。** 表默认值是 `auth.uid()`，由服务端填。
如果客户端自己传 `owner_id`，RLS 的 `WITH CHECK (owner_id = auth.uid())` 会直接拒绝。

### 5.4 数据隔离

所有业务表都开了 RLS，策略是 `owner_id = auth.uid()`。
**这意味着数据隔离是数据库层强制的，不靠前端自觉** —— 客户端拿不到别人的数据，写不进别人的行。

所以：

- 不要在前端做「按用户过滤」的逻辑（没必要，也不可靠）
- 不要试图传 `owner_id` 来指定归属
- 查询时不需要自己加 `where owner_id = ...`，RLS 已经限制了

## 6. 同步协议（**最容易做错的部分，请逐字遵守**）

网页版已经有一套成熟的「本地为主 + 云端同步」实现。小程序**必须遵守同一套协议**，否则两端会互相覆盖对方的改动。

### 6.1 顺序：**先推后拉**

```
① 推：把本地未同步的改动上传（可重试，失败留在队列里）
② 拉：按 updated_at 倒序拉云端，合并
```

**顺序不能反。** 反过来做的话，本轮本地的改动会被拉回来的旧版本盖掉。

### 6.2 推送

先取云端已有的行拿到行 id 映射：

```js
const { data: rows } = await db.from('courses').select('id, course_id').limit(1000)
const existing = new Map()
rows.forEach(r => { if (r.course_id) existing.set(r.course_id, r.id) })
```

然后对每个待同步的课程：

```js
const rid = existing.get(course.id)
if (rid) {
  await db.from('courses')
    .update({ data: course, updated_at: new Date().toISOString() })
    .eq('id', rid)
} else {
  await db.from('courses').insert({ course_id: course.id, data: course })
}
```

推送失败的项**留在队列里**，不要丢弃（离线时不丢数据）。

### 6.3 删除用墓碑，不能用「删除成功即完事」

本地删除一门课后，云端也要删，但**必须在本地留下墓碑记录**（课程 id + 删除时间戳）：

```js
await db.from('courses').delete().eq('id', rid)
// 同时在本地记下：tombstone[courseId] = 删除时间
```

拉取合并时按墓碑判断：

```
如果本地删过这门课，且删除时间 >= 云端这一版的 updatedAt
  → 不复活（丢掉云端的这一版）
否则（云端比删除还新 —— 说明另一台设备删了又改）
  → 云端赢，保留
```

**没有墓碑会出现的 bug**：在手机上删了一门课，网页版拉取时又把它「同步」回来，用户会觉得删除不生效。

### 6.4 拉取合并

```js
const { data: rows } = await db
  .from('courses')
  .select('data')
  .order('updated_at', { ascending: false })
  .limit(500)
```

合并规则（优先级从高到低）：

1. 本地**未同步**的改动
2. `updatedAt` 较新的那一份
3. 墓碑规则（见 §6.3）

### 6.5 并发保护

同步函数**同一时刻只能跑一次**（用一个运行中标志位拦住）。并发跑两次会互相覆盖。

### 6.6 账号隔离（**这条有历史事故，务必做对**）

所有本地缓存必须**按账号命名空间隔离**。

网页版这里踩过一次真实的串数据事故，修复方式是给本地存储 key 加上账号前缀。**小程序必须做同样的事。**

- 本地缓存 key 形如 `u_<userId>_courses`；未登录用 `guest`
- **不要用邮箱或手机号做 key 前缀**（含隐私，且会因改号而失联）
- 切换账号时，**读不到就是空** —— 绝不能回落到「上一个账号留下的那份」

**未登录时不要写埋点。** 见下面 §7.2 的那个坑。

## 7. 埋点（`analytics_events`）

### 7.1 事件名必须落在白名单里（**这是硬约束，不是风格建议**）

**不在名单里的事件名不会上报**，写了等于没埋。

所以「与网页版对齐」不是措辞问题，是**能不能拿到数据**的问题。

### 7.2 守卫的真实行为（不是静默丢弃）

```js
const __trackWarned = {}

function trackGuard(name) {
  if (TRACK_EVENTS.indexOf(name) >= 0) return true
  if (!__trackWarned[name]) {
    __trackWarned[name] = true
    console.warn('[track] 未在白名单里的事件名（本条不会上报）: ' + name)
  }
  return false
}
```

- 在白名单里 → 放行
- 不在 → **告警一次**（同类只报一次，不刷屏）后返回 `false`，**该条不上报**

> 网页版在 2026-09-24 之前是**静默 return**，后果是 `tts_unavailable` 这类重要信号被无声丢掉、谁都不知道。
> 现在改成了告警。但「拿不到数据」这点没变 —— **写错名字依然等于没埋**。

**要求**：小程序侧实现等价的白名单守卫，写错名字**当场告警**，不要无声丢掉。

### 7.3 登录前的事件：先落队列，登录后补报

注册环节的埋点发生在**登录之前**，而 `track()` 要求已登录（否则 RLS 写不进去）。
网页版的处理方式是**先存本地队列，登录成功后补报一次**：

```js
const TRACK_PENDING_KEY = 'lingxi.track.pending.v1'

function trackLater(name, props) {
  if (!trackGuard(name)) return
  const q = JSON.parse(localStorage.getItem(TRACK_PENDING_KEY) || '[]')
  q.push({ name, props: props || {}, at: Date.now() })
  localStorage.setItem(TRACK_PENDING_KEY, JSON.stringify(q.slice(-20)))   // 只留最近 20 条
}

function flushPendingTracks() {
  const q = JSON.parse(localStorage.getItem(TRACK_PENDING_KEY) || '[]')
  if (!q.length) return
  localStorage.removeItem(TRACK_PENDING_KEY)
  q.slice(-20).forEach((e) => track(e.name, e.props))
}
```

**小程序要做同样的事**（换成 `wx.setStorageSync`），否则「被拦的一次性邮箱」这类**注册前**的风控事件永远统计不到，
黑名单就没法按数据维护。

⚠️ 但**不要**把它理解成「未登录也可以写埋点」—— 队列只在**本地**，真正的写入仍然只发生在登录之后。

### 7.4 `props` 的限制（照做，否则两端口径不一致）

源码里对 `props` 有明确裁剪，小程序要一致：

| 限制 | 值 |
|---|---|
| 最多取几个 key | **前 8 个**（`Object.keys(props).slice(0, 8)`） |
| 字符串值最大长度 | **300 字符**（超出截断） |
| `undefined` / `null` 的 key | 直接丢掉，不写入 |
| 埋点是否 `await` | **不 await** —— 埋点绝不参与交互时序，失败静默 |

### 7.5 ⚠️ 一个真实存在的缺陷，不要照抄

**未登录时不要往 `analytics_events` 写数据。**

原因：未登录会话的 `auth.uid()` 返回的是**字符串 `'anon'`**（实测，不是 `NULL`），而这张表的 RLS 策略是 `owner_id = auth.uid()`。
结果是所有未登录访客共享同一个 `'anon'` 租户 —— 互相能看到对方的埋点。

实测确认：未登录状态下

- `GET /.cloud/database/rest/analytics_events` → **HTTP 200**，返回 14 行他人的埋点（含课程标题）
- `POST /.cloud/database/rest/analytics_events` → **HTTP 201 写入成功**

网页版靠应用层拦住（未登录直接 `return`），但**数据库层是敞开的**。

**对你们的要求：**

- 写埋点前先判断登录态（`track()` 里那层 `memReady()` 门禁要等价实现）
- 不要把敏感信息放进 `props`（当前 `props` 里有课程标题，这已经偏多）
- 登录前的事件走 §7.3 的本地队列，不要直写云端

> 这个缺陷已记录，会作为独立问题处理。你们**不要**去改 RLS（那是网页版和数据层的事），只需在客户端守住「未登录不写云端」。

## 8. AI 能力（LLM 网关）

平台提供免密钥的模型调用，**不需要你们申请任何 API Key**，走的是登录用户的配额。

### 8.1 两个接口

| 方法 | 路径 | 说明 |

| `GET` | `/.cloud/llm/models` | 模型清单（实测返回约 21KB 的模型数组） |
| `POST` | `/.cloud/llm/chat/completions` | 对话补全 |

// 模型清单
const models = await cloud.llm.models.list()

// 对话（流式）
for await (const chunk of cloud.llm.chat.completions.create(params)) {
  // 逐块处理
}

### 8.3 模型

模型清单由服务端下发，其中 `id: "auto"` 是「自动为任务匹配最优模型」。
**不要把模型 id 写死在代码里**，从 `models.list()` 的结果里取。

- 引导强度（更多引导 / 均衡 / 更多自主）
- 元认知提问（「哪一步让你困惑？」）
- **费曼学习法**（见 §10）
- 苏格拉底提问

### 9.4 小程序端注意

- WXML 里用 `<text>` / `<view>`，**没有 `<b>` 标签** —— 要加粗用 `<text class="em">` 配样式

## 10. 费曼「讲给我听」（两端规则必须一致）

这是网页版已上线的功能，小程序要做**同样的规则**，否则同一个环节在两端判定不一样。

### 10.1 四步

1. 选定概念
2. 讲给一个**完全不懂的人**听
3. 找出卡壳的地方
4. 回补，并用类比重讲

### 10.2 与苏格拉底提问的区别

| | 费曼 | 苏格拉底复述 |
|---|---|---|
| 能不能用术语 | **不能**，必须说人话 | 可以 |
| 讲给谁 | 外行 | 老师 |
| 验证什么 | 是否真的理解 | 这一轮有没有听懂 |

### 10.3 AI 的角色与判据

- AI 扮演**完全不懂的初学者**，只提问、不替学生总结
- **验收不能用听众的角色来做**（让一个「什么都不知道的人」评价讲解质量是错的）—— 要另起一次调用，用第二个提示词做验收

### 10.4 ⚠️ 必须有一道确定性守卫

提示词是**请求**，不是**保证**。模型经常会去复述知识点清单，而不是真的评价学生讲得怎么样。

所以必须加一道可数的确定性守卫：**由代码数「学生讲了几句、几个字」**，达不到门槛就判定「没讲够」。

| 参数 | 值 | 说明 |
|---|---|---|
| `MIN_TURNS` | 2 | 至少 2 轮学生发言 |
| `MIN_CHARS` | 60 | 学生发言累计至少 60 字（**去掉空白后**计数） |

**上面两项「阈值」本身要对，下面三条「口径」也要对 —— 任意一条不同，同一个学生在两端就会被判出不同结果：**

| 项 | 网页版实现（照此对齐） |
|---|---|
| 谁算「学生发言」 | `messages` 里 `role === 'user'` 的条目（**不是** `'student'`） |
| 字数怎么数 | `content` 去掉所有空白字符后取 `.length` |
| 门槛 | 两项都要满足（`&&`，不是 `||`） |

对应网页版源码：常量 `FEYNTALK_MIN_TURNS` / `FEYNTALK_MIN_CHARS`，
统计函数 `feynTalkStudentStats(talk)`，守卫函数 `guardFeynTalkVerdict(v, stats)`。

**不达标时要把 `explained` 和 `skipped` 一起清空**（只清 `explained` 不够 —— 学生都没怎么讲，说他「绕过了什么」同样是凭空判断），并标记 `insufficient: true`。

### 10.5 ★ 判据必须来自可信来源 —— 以及这个「服务端」到底从哪来

**原则（不变）：**

网页版是纯前端应用，它的守卫只能基于**本地内存里的对话记录** —— 这是它的结构决定的，不是疏忽。

而**判据不能由被检验的一方提供**：如果采信客户端传来的 `stats` / `turns` / `chars`，
这个守卫就等于没有 —— 客户端改一个数字就能让「没讲够」变成「讲得很好」，
而一次**没真正发生的检验**会看起来像是发生了。那比不给结论更糟。

> 项目里另一处同类教训是配额校验：额度检查如果在客户端做，同样形同虚设。

**⚠️ 这一段是本规格书此前的疏漏，现更正：**

本规格书写了「守卫必须放服务端」，却**没有说明服务端从哪来**。
实测查清了平台的真实能力边界：

| 能力 | 是否存在 | 实测依据 |
|---|---|---|
| 云服务提供自定义函数 / 服务端代码 | ❌ **没有** | 云服务只有 `auth` / `database` / `storage` / `llm` 四个模块 |
| 数据库 RPC 发外部 HTTP | ❌ **不行** | 实测数据库只装了 `plpgsql` 扩展，**没有 `pg_net` / `http`** |
| 客户端直连 LLM | ✅ 可以 | 见 §8 —— 但这样 history 只存在于客户端 |

**结论：如果 AI 调用由客户端直连 `cloud.llm`，服务端就没有 history 的数据源，
「服务端自己数」这条就无处落地。** 这不是实现难度问题，是缺承载。

**两条出路，请与我们确认后选一条：**

**出路 A —— 引入微信云函数当服务端（能真正满足 §10.5）**

- 微信小程序本就可以开通微信云开发，用**云函数**经手 AI 调用
- 云函数把学生每一轮发言**记在自己的存储里**（微信云数据库），再调 LLM 拿回复
- 判定时，云函数数**自己记的** history → 客户端伪造不了
- 代价：
  1. 需要开通一个微信云开发环境
  2. **云函数不支持流式返回**，「逐字出字」的体验会退化为「等完整回复」——
     若要保留打字感，只能做成「云函数一次性返回 + 前端做打字机效果」来折中

**出路 B —— 接受客户端守卫，并如实记为未完成项（当前的现实）**

- 客户端守卫能挡住**误操作**（学生随便讲两句就点完成），**挡不住改代码的人**
- 在服务端就位前，§12 的 C 组末项（伪造 `stats`）**应记为未完成，不要标绿**

**在承载确定之前，请这样实现：**

1. 客户端守卫照 §10.4 做，与网页版**逐字等价**（含 `role` 与去空白口径）
2. 守卫在调模型**之前**先执行一次 —— 讲太少时根本不给模型编结论的机会
3. 拿到模型结论后再过一遍（双重保险）
4. 把**服务端接法的完整函数体**写好放在注释里，承载到位后直接搬，调用方无需改动

**验收会测这一条**：客户端伪造一个超大的 `stats` 提交，必须**仍然**被判「没讲够」（§12 C 组末项）。
在出路 A 落地前，这一项无法通过 —— 请如实标注，不要用它来证明功能的可靠性。

## 12. 验收清单

交付前请逐条自测，并在交付说明里给出每一条的结果。

**A. 登录**

- [ ] 新手机号：能收到验证码，验证后建立会话
- [ ] 已注册手机号：能收到验证码，验证后进到**已有数据**（能看到网页版建的课程）
- [ ] 输错验证码：报「验证码不正确或已过期」，**不重发短信**，会话不建立
- [ ] 未获取验证码就点登录：提示先获取，**不发请求**
- [ ] 改了手机号后点登录：提示重新获取，**不拿旧 handle 去验证**
- [ ] 60 秒内重复发送：报「发送过于频繁」，不崩
- [ ] 发送中 / 提交中按钮禁用，无重复请求
- [ ] 杀掉小程序重进：会话恢复，无需重新登录
- [ ] 退出登录后：受保护页面回到登录态，本地不再显示上一账号的数据

**B. 数据**

- [ ] 课程列表取到的是当前账号的课程，**看不到别人的**
- [ ] 网页版改一门课的进度 → 小程序下拉刷新后能看到新进度
- [ ] 小程序改一门课的进度 → 网页版刷新后能看到
- [ ] 在网页版删除一门课 → 小程序同步后**不再出现**，且不会复活
- [ ] 小程序删除一门课 → 网页版同步后也删除
- [ ] 断网时改动 → 恢复网络后能同步上去（不丢）
- [ ] 切换账号后，前一个账号的课程**完全不可见**

**C. AI 与费曼**

- [ ] 上课能流式出字（不是等半天一次性出现）
- [ ] 「讲给我听」里 AI 扮演的是不懂的人，**不替学生总结**
- [ ] 学生只讲一两句短话 → 验收判「没讲够」，**不给通过**
- [ ] 讲够内容后 → 验收给出结论
- [ ] 客户端伪造统计值（把 `stats` 传大）→ **仍被判没讲够**（守卫在服务端）
  - ⚠️ **这一项在服务端承载落地前无法通过**（见 §10.5）。没落地就如实标「未完成」，不要标绿。
- [ ] AI 失败时：「讲给我听」入口依然可见（它不依赖 AI 总结）

**D. 工程**

- [ ] `app.json` 含 `"lazyCodeLoading": "requiredComponents"`
- [ ] `pages` 里登记的每个页面都有真实 `.wxml` + `.js`
- [ ] 没有 `localStorage` / `document` / `window` 的用法
- [ ] 没手写 `wx.request` 打数据面接口
- [ ] 没有硬编码的手机号、token、用户 id
