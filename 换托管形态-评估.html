灵犀课堂 · 「换托管形态」评估

评估时间 2026-10-08 · 线上 bb6ae4d03fbd4b109cbbe6dbbc84502d.app.workbuddy.host
评估目标：把发布形态从 纯静态托管 换成 http-service（单端口 Node/Python 服务），以换取第 1/2/6 项（gzip+缓存、安全响应头、Origin 收紧）。
结论：不建议为了「响应头 + gzip」换形态。 阻碍不是工作量 —— 仓库里 tools/serve.js 已经把项 1/2/6 实现好、本地实跑通过； 阻碍是域名会变，而 web 应用的登录只在「应用注册的发布域名」上生效（官方文档硬约束，前端无解）， 以及找不到「把新域名重新绑定为该应用 release domain」的入口。 次要代价：本地 7 族状态（含未同步的编辑队列）随 origin 丢失，且要把 serve.js 的拒访黑名单升级为白名单。 若目标只是首屏体积，有一条不动形态、零风险的等效路径 —— 见第五节。
⇒ 正确顺序：先拿到「新域名能否注册为 release domain」的答案，再谈换不换。

一、能拿到什么（收益）

项静态托管现状（实测）换成 http-service 后
gzip / br 压缩 无。显式发 Accept-Encoding: gzip, br, deflate 仍无 Content-Encoding 可自行压缩（首屏四件 937 KB → 约 250 KB）
安全响应头 X-Frame-Options/X-Content-Type-Options/HSTS/Referrer-Policy/CSP(HTTP 形式) 全缺 全部可设，含 meta 形式无效的 frame-ancestors
缓存策略 无 Cache-Control/ETag；但 If-Modified-Since → 304 实测可用 可显式设 Cache-Control（带指纹的静态资源可长缓存）
Origin 反射（第 6 项） 401 响应回显任意 Origin（网关行为） 前端服务自己发 CORS 时可收敛；但 /.cloud/* 是平台云网关，仍不受我们控制
实测 第 2 项「平台无法设置响应头」应限定范围：静态分发层确实不设； 但 /.cloud/* 这个云服务网关是设的 —— 它返回 X-Content-Type-Options: nosniff、Access-Control-Expose-Headers、 Vary: Origin。⇒ 平台有这个能力，只是静态资源路由没启用。 这条可以作为对方第 1 个问题的补充证据（不是「完全没有」，是「静态路由没有」）。

二、代价与风险（按严重度）

① 域名几乎必然变更 已有事故记录

2026-09-28 已踩过：给静态站加 package.json 后平台判成 http-service， 域名被换掉、旧链接直接失效（domainPrefix → sandboxId）。 本次是要主动换成该形态，所以应按「域名必变」规划。

② 登录会断 —— 这是硬约束，前端无解 官方文档条款

For a web app, auth is supported only on the application's registered HTTPS release domain.
WorkBuddy preview and localhost are not supported because they do not have the registered
Origin/callback binding.

出处：本机技能 cloud-service/references/auth/code-generation.md:40

实测 当前域名上的云挂载是真实存在且已注册的： GET /.cloud/auth/v1/user/me → HTTP 401（不是 404，说明该端点存在且要求鉴权）； 而 /.cloud/v1/health 这类未挂载路径回 404 + {"error":"invalid_request", ...}。
SDK 的路径映射为 auth: /.cloud/auth · database: /.cloud/database/rest · storage: /.cloud/storage · llm: /.cloud/llm。
⇒ 换域名后，新域名不会被自动认成该应用的注册发布域名， 登录（含手机号验证码）会失败。必须在平台侧把新域名重新绑定为该应用的 release domain 才能恢复 —— 这一步能不能做、怎么做，我没有找到文档入口，是本次评估最大的未知项。

③ 本地状态全部丢失（绑定 origin）

键内容换域名后
workbuddy-cloud.session.*登录会话（SDK 写入）丢失 → 全体用户必须重新登录（要真实手机号+验证码）
lingxi_sync_queue未同步的本地编辑队列丢失 → 这些改动永远不会到达云端
lingxi_theme / lingxi_tts / lingxi_tts_rate / lingxi_teach_lang / lingxi_feynman / lingxi_guide / lingxi_avatar_style个人偏好重置为默认值（可接受，但用户会感觉"设置丢了"）

④ 云端数据本身是安全的（这条是好消息）

题库 / 课程 / 学习档案不在 localStorage 里（实测：本地键只有上面那几族）。 业务数据全部走云库 —— app.js 里有 23 处 .from(、14 处 .select(、 6 处 .insert(、3 处 .rpc(。 而应用实例由 publishableKey 标识 （wbpk_Pq3DhJIr74vvC8YpuqkMPA_…，其中 Pq3DhJIr74vvC8YpuqkMPA 即应用 id）， 不是由域名标识。
⇒ 只要新域名能通过认证到同一个应用，历史数据不丢；风险点在「能不能认证到」，不在「数据在不在」。

⑤ 服务端**不用从零写** —— 这条是修正，不是风险

实测（读源码 + 本地实跑） 仓库里已经有 tools/serve.js（323 行，package.json 的 start 就是它）， 本地 PORT=3112 node tools/serve.js 实跑通过，启动即宣告： 
[lingxi] 已启用：br/gzip 压缩、ETag + 条件请求、安全响应头（frame-ancestors 'self'）
它已经实现的正是第 1/2/6 项：
  • 压缩：br/gzip，且正确解析 q 值（注释里记着踩过的坑：br;q=0 用正则会被误命中，而 q=0 是明确拒绝）；压缩结果带 mtime/size 缓存；压完变大就不压。
  • 缓存：ETag + 条件请求 304 + Vary: Accept-Encoding；HTML 用 no-cache、资源用 max-age=3600，并明确写明为什么此时不能用 immutable（裸路径无指纹，会被永久缓存成旧版）。
  • 安全头：frame-ancestors 'self' + X-Frame-Options: SAMEORIGIN + nosniff + Referrer-Policy + HSTS + Permissions-Policy。
  • 静态托管白送的那些也都有：目录请求 → index.html、SPA 回落、Content-Type 判表、 .. 与编码变体的目录穿越双层防护、/.cloud 误入静态服务时显式回 502 并写明原因（而不是回落 HTML 让 SDK 拿着 HTML 去 JSON.parse）。
⇒ 所以换形态的实现工作量很小。真正的阻碍只有第二节的①（域名变更）和②（auth 域名绑定）， 与「要不要写代码」无关。

⑥ 但它是一份**黑名单**（这条仍是真风险）

serve.js 用 DENY_TOP_DIRS = {tests, tools, sql, node_modules, .git, _quality} + DENY_ROOT_FILES = {package.json, package-lock.json, _mut-check.js, HANDOFF.md} 拒访开发产物。 方向是对的（回 404 不回 403、且放在回落 index.html 之前），但它是穷举式的黑名单 —— fail-open： 以后新增任何一个不该公开的目录/文件（新的 SQL 目录、日志、导出、密钥文件）， 不写进这个集合就会自动被公开托管。

换形态时必须同时把这份黑名单升级成白名单（只服务 index.html/css/js/assets/vendor， 其余一律 404），并加「集合相等」漂移守卫与两个方向的变异验证。 这是把「平台替我挡」换成「我自己挡」时唯一必须补的功课 —— 其余部分 serve.js 已经做好了。

另外 serve.js 的注释里有一条今天复现不出来的实测依据（说 /.cloud/** 返回 frame-ancestors + X-Frame-Options）。我已在源码里更正： 今天对 /.cloud/ 下 5 个路径逐个打，全部 401，这两个头命中数均为 0，只有 nosniff。 取值本身仍合理，但那句话不能再当依据。

三、唯一「零风险试水」路径

有一个办法能不动现有线上链接就把它试出来：把项目复制到另一个目录发布 —— 平台按 directory 认应用，新目录 = 新应用 = 新链接（现有 bb6ae4d0… 不受影响）。

但这条试水路径本身有个必须先验证的关键未知项： 新应用能不能拿到 /.cloud 云挂载与 auth 域名绑定？ 按第①②条，大概率拿不到（auth 只在注册的 release domain 上生效）—— 那么试出来的「http-service 站点」会是一个能开页面但登不上、用不了云能力的空壳， 这恰恰是对方报告里第 4 项重新表述过的残余风险。
⇒ 试水前，应先向平台确认两件事：(a) 新域名能否被注册为该应用的 release domain； (b) 换形态后原应用 id 与新域名如何对应。

四、如果仍决定换：迁移清单

  • 先备份：导出云库（14 个课件、题库、档案、课程）与当前 index.html/css/js 的 SHA。
  • 公告 + 预案：用户需重新登录；旧链接会失效。若已有真实付费用户，这步不能省。
  • 把 serve.js 的黑名单升级为白名单：只服务 index.html/css/js/assets/vendor，其余 404； 加「集合相等」漂移守卫 + 两个方向的变异验证（该漏的漏、该挡的挡）。
  • 确认 BaaS 无外部依赖：serve.js 已对 /.cloud 误入回 502 —— 这条正好是本次最大的未知项的探针， 发布后必须先打 /.cloud/auth/v1/settings 看是 401（网关接管 ✓）还是 502（没接管 ✗）。
  • 逐项验收：gzip/br 生效、六个安全头齐全、Cache-Control 与 304 生效、 /.cloud/auth 可达且能真正登录成功、本地 7 族键在新域名下的表现符合预期。
  • 保留回滚：静态托管那份随时能重新发布回去；域名若已变更，回滚也要一并回退域名。

五、更划算的替代：不动形态，把首屏体积砍掉

如果换形态的真实动机是「首屏慢 / 冷启动约 50s」，那么有一条零风险的等效路径 —— 构建期压缩产物：

文件当前是否已压缩可省
js/app.js683,238 B 否（12,966 行，平均行长 39 字符，含 1,000 行注释）去注释+空白+短化标识符，预计省 35~45%
css/style.css144,537 B 否（2,849 行，181 行注释）预计省 20~25%
vendor/workbuddy-cloud-sdk.global.js62,057 B 是（6 行，平均行长 8,864）—
index.html69,111 B否较小
实测 首屏四件资源合计 958,943 B（≈937 KB），其中 app.js 占 71%。 在静态托管下压缩产物是唯一能自己做的事：预计可从 ~937 KB 降到 约 500~550 KB， 不需要换域名、不需要重新登录、不影响任何已有功能。
（补充：If-Modified-Since → 304 已实测可用，所以重复访问本就不会重下这些字节 —— 真正受影响的是首次/冷启动。压缩产物只对首次有效，正好打在痛点上。）

六、建议

  1. 不做形态切换（至少现在不做）。理由不是工作量（tools/serve.js 已把项 1/2/6 实现好、本地实跑通过）， 而是第二节①②这两条前端无解的硬约束：域名会变、而 web 应用的 auth 只在「应用注册的发布域名」上生效， 换域名意味着全体用户登不上，且我找不到重新绑定的入口。
    ⇒ 决策的正确顺序是：先拿到「新域名能否注册为该应用 release domain」的答案，再谈换不换。 拿到肯定答案后，这次切换的成本会低得多（服务端已就绪，只需补一份白名单）。
  2. 做：app.js/style.css 的构建期压缩 —— 零风险拿到首屏体积的主要收益。
  3. 已落地：meta referrer（第 2 项在静态托管下唯一可行的一条）。 加上已存在的 CSP meta（10 条指令，原有资产），connect-src/script-src 层面已有约束。
  4. 向平台确认（对方第 1 个问题的正式回答）： 已确认没有「自定义响应头 / edge 规则」配置入口（证据：本机 sites 技能全文零命中； 发布工具入参只有 directory/language/port/installCmd/startCmd/entryHtml/appName/domainPrefix）。 待确认的是静态路由能否支持响应头——因为 /.cloud/* 证明平台具备该能力（至少设了 nosniff）。
  5. clickjacking（残余风险 1）：在静态托管下无解，先按业务判断接受； 若哪天站点开始处理敏感操作，再把它作为换形态的唯一理由重新评估 —— 那时 serve.js 直接可用。
